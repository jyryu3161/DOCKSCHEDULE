# 미해결 문제

## 1. api를 여러 프로세스로 늘리면 로그인 제한과 pose 분석 제한이 약해진다
- 조건: api를 worker 2개 이상으로 실행.
- 증상: 로그인·가입 횟수 제한(분당 15회/60회)이 프로세스별로 따로 계산되어 실제 허용 횟수가 worker 수만큼 늘고, pose 상호작용 분석의 "한 번에 하나" 제한과 최근 32개 캐시도 프로세스별로 적용되어 동시 분석이 늘어난다.
- 영향: 비밀번호 대입 시도 제한 약화, 조회용 분석이 CPU를 더 쓴다.
- 지금 해결하지 않는 이유: 현재 배포는 api 단일 프로세스(uvicorn 1개)가 전제이며 학생 40명 규모에서 확장이 필요하지 않다. 확장하려면 제한을 Redis나 DB로 옮겨야 한다.

## 2. CPU 요구가 큰 작업이 계속 건너뛰어질 수 있다 (코드 분석 기준, 관측된 적 없음)
- 조건: 어떤 학생의 `cpu_override`가 크고(예: 8) 다른 학생들이 4 CPU 작업을 계속 이어서 실행해 비어 있는 CPU가 그 값보다 작은 상태가 유지될 때.
- 증상: 스케줄러가 CPU가 모자라는 작업은 건너뛰고 뒤의 작은 작업을 먼저 시작하므로(`choose_tasks`), 큰 작업이 계속 `queued`에 머물 수 있다.
- 영향: 해당 학생의 작업 대기 시간이 무기한 늘 수 있다.
- 지금 해결하지 않는 이유: 정책 결정(엄격한 순서 보장 vs 처리량)이 필요하고 현재 설정(모두 기본 CPU 4)에서는 재현되지 않는다. 관리자가 `cpu_override`를 쓸 때 수동으로 조정하거나 한도 안에서 남는 CPU를 확보해야 한다.

## 3. 의존 라이브러리의 폐기 예고 경고
- 조건: 테스트 실행 시 항상.
- 증상: Starlette TestClient의 `httpx` 사용 폐기 경고, MDAnalysis의 `MDAnalysis.topology.tables` 이동(3.0에서 제거) 경고.
- 영향: 해당 라이브러리를 상위 버전으로 올릴 때 테스트·상호작용 분석이 깨질 수 있다.
- 지금 해결하지 않는 이유: 아직 제거되지 않았고 `uv.lock`으로 버전이 고정되어 있다. 의존성 갱신 시 처리한다.

## 4. 40명 동시 실제 docking 부하가 검증되지 않았다
- 조건: 학생 다수가 동시에 큰 library를 제출.
- 증상: 알려진 것이 없다. 처리 시간(80만 개 약 5.9일, 단순 외삽)과 메모리·디스크 사용은 실측이 아닌 추정이다.
- 영향: 수업 일정 계산이 틀릴 수 있다.
- 지금 해결하지 않는 이유: 학생 40명이 참여하는 실제 부하 시험이 필요하고 서버를 오래 점유한다.

## 5. 업로드·receptor를 지울 수단이 없어 학생별 저장 한도에 영구 누적된다
- 조건: 학생이 PDB·library 업로드나 전처리를 반복해 `user_storage_limit_gb`(기본 10)에 도달.
- 증상: 새 업로드·전처리·제출이 "학생별 저장 공간 한도" 오류로 거절되고, 진행 중이던 작업은 다음 화합물 시작 때 `failed`가 된다. 삭제할 수 있는 것은 screening 작업뿐이며 보존 기간 자동 삭제도 screening만 대상이다.
- 영향: 해당 학생이 더 이상 작업을 만들 수 없다. 풀려면 관리자가 한도를 올리거나 DB·디스크를 직접 정리해야 한다.
- 지금 해결하지 않는 이유: 학생 본인의 업로드·단백질 삭제 기능이 계획되어 있다(진행 현황의 남은 일 1번). 그 전까지의 운영 방침(한도 상향 vs 수동 정리)은 아직 정해지지 않았다.
