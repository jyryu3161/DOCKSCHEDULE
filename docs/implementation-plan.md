# DOCKSCHEDULE 구현 계획

DOCKSCHEDULE은 학생이 단백질과 화합물 library를 제출하고 QuickVina docking 결과를 확인하는 수업용 플랫폼이다. 현재 서버에서 학내망 IP와 포트로 제공하며, 40명이 각각 최대 100,000개 화합물을 제출하는 장시간 작업을 지원한다. 이 문서는 2026년 10월 14일 인터뷰와 후속 변경을 반영한다. 핵심 기능을 구현하고 배포했으며 검증 범위는 [검증 기록](validation.md)에 정리했다.

## 확정된 요구사항

| 항목 | 동작 |
| --- | --- |
| 회원 관리 | 학생이 가입하고 관리자가 승인한 뒤 작업을 제출한다. |
| 관리자 | ID는 `admin`, 초기 비밀번호는 사용자가 지정한 값으로 설치 시 주입한다. |
| 운영 환경 | 현재 Linux 서버, 학내망 IP와 포트로 접속한다. 장시간 실행을 허용한다. |
| 규모 | 학생 약 40명, 작업당 library 상한은 100,000개이며 관리자가 낮출 수 있다. 초기 예상 규모는 학생당 20,000개였다. |
| 단백질 | 미전처리 PDB를 받아 결손 잔기와 원자 복구부터 처리한다. 서열의 근거는 업로드한 PDB에 한정한다. |
| 구성 성분 | 물과 기존 리간드는 기본 제거한다. 금속과 보조인자는 목록을 보여주고 유지 여부를 선택한다. |
| 결합 위치 | 중심 좌표 직접 입력 또는 연동된 sequence viewer와 structure viewer에서 잔기를 선택한다. |
| Library | CSV, TSV 등 구분자로 나뉜 파일을 업로드하고 구분자, CID 컬럼, SMILES 컬럼을 지정한다. |
| Conformer | RDKit으로 생성하고 에너지 최소화한 3D 구조를 뜻한다. 화합물당 기본 1개이며 변경할 수 있다. |
| Docking 결과 | 화합물당 최상의 docking pose 1개를 제공한다. 여러 conformer를 사용하면 전체 conformer 결과 중 최상을 고른다. |
| 병렬 실행 | 관리자가 전체 CPU 한도, 동시 실행 학생 수, 학생별 docking CPU 수를 지정한다. |
| 학생 내부 순서 | 한 학생의 화합물과 각 화합물의 conformer는 순차 처리한다. 같은 학생의 작업은 동시에 여러 개 실행하지 않는다. |
| 결과 제공 | 단백질과 최상 pose를 3D viewer로 확인하고 affinity를 표시한다. 전체 library 점수를 다운로드한다. |

처음의 학생 간 완전 순차 실행 요구는 관리자 설정이 가능한 병렬 실행으로 확장되었다. 동시 학생 수를 1로 설정하면 완전 순차 모드가 된다.

## 학생과 관리자의 사용 흐름

학생은 가입 후 승인 상태를 확인한다. 승인 후 PDB를 업로드하고 사용할 chain과 구성 성분을 선택한다. 단백질 전처리는 CPU 자원을 배정받아 수행한다. 완료되면 복구된 구조와 서열을 확인하고 결합 위치와 grid box를 확정한다. 전처리 작업은 완료 시 실행 자원을 반환하므로 학생의 화면 입력을 기다리면서 CPU 자리를 점유하지 않는다.

학생은 library를 올리고 구분자와 컬럼을 지정한다. 미리보기에서 파싱 결과와 입력 오류를 확인한 뒤 conformer 수와 docking 옵션을 설정하고 제출한다. 순서가 되면 계산을 시작하며, 완료된 화합물 결과는 전체 작업이 끝나기 전에도 볼 수 있다.

관리자는 가입 승인과 거절, 계정 정지, CPU 배분, 작업 대기열, 실패 원인, 디스크 사용량을 관리한다. 학생별 CPU 기본값과 개별 설정을 제공하고, 작업 취소 및 실패 항목 재시도를 지원한다. 학생은 본인 자료에 접근하고 관리자는 전체 작업을 확인한다.

## 단백질 자동 전처리

PDBFixer와 OpenMM을 전처리에 사용한다. PDBFixer는 누락된 원자와 loop 생성 기능을 제공하며, 결손 잔기를 식별할 때 `SEQRES` 서열과 원자 기록을 비교한다. [PDBFixer 설명](https://github.com/openmm/pdbfixer), [PDBFixer 매뉴얼](https://github.com/openmm/pdbfixer/blob/master/Manual.html)

전처리 순서는 구조 검사, model과 chain 선택, 대체 위치 정리, 구성 성분 처리, 결손 잔기와 원자 복구, 수소 추가, 구조 검사, receptor PDBQT 생성으로 구성한다. 수소 추가의 pH 기본값은 7.4로 제안하고 변경 가능하게 한다. 이미 관측된 원자의 좌표를 가능한 한 보존하며 추가한 원자를 정리한다. 원본 PDB, 전처리 PDB, PDBQT, 변경 내역을 보관한다.

`SEQRES`가 있으면 실제 원자 기록과 비교해 서열이 확인되는 결손 구간을 복구한다. `ATOM` 기록만 있는 파일에서는 존재하는 잔기의 누락 원자를 보완하되, 잔기 번호가 비어 있다는 이유만으로 아미노산 종류를 만들어 넣지 않는다. 결손 여부나 서열을 확정할 수 없으면 그 한계를 전처리 보고서에 표시한다. 외부 FASTA 입력이나 외부 서열 조회를 필수로 하지 않는다.

복구 구간은 viewer에서 원래 좌표가 있던 잔기와 구분해 표시한다. 긴 결손 구간, 큰 충돌, 비정상 결합, 지원하지 않는 화학 성분은 검사 결과로 남긴다. 구조 생성에 실패하거나 검증을 통과하지 못하면 성공으로 표시하지 않고 수정 가능한 오류를 제공한다. 자동 생성된 좌표를 실험적으로 관측된 구조로 취급하지 않는다.

금속과 보조인자를 유지하는 선택은 해당 성분의 전처리와 qvina 원자형 지원을 검사한 뒤 반영한다. 유지 요청한 성분을 조용히 삭제하지 않는다. 알려지지 않은 HETATM 성분은 이름만으로 리간드라고 단정하지 않고 검토 목록에 표시한다.

## 서열과 구조에서 결합 위치 지정

중심 좌표 `x`, `y`, `z`와 박스 크기 `size_x`, `size_y`, `size_z`를 Å 단위로 입력한다. Sequence viewer와 structure viewer의 잔기 선택은 양방향으로 동기화한다. 여러 잔기 선택을 지원하고, 초기 구현에서는 선택한 잔기의 heavy atom 좌표 평균을 중심으로 제안한다. 사용자는 제안된 중심과 박스 크기를 수정할 수 있다.

화면에는 grid box를 실시간 표시한다. 잔기의 식별자는 model, chain, residue number, insertion code를 포함한다. 전처리 전후 잔기 대응표를 유지하며, 좌표가 없는 잔기는 위치 계산에 사용하지 않는다. Grid는 최종 전처리 구조 기준으로 저장하고 작업 제출 후에는 해당 구조와 설정을 고정한다.

## Library와 화합물 처리

구분자는 쉼표, 탭, 세미콜론 및 사용자 지정 문자를 지원하고 header 유무와 인코딩 선택을 제공한다. 구분자 선택 결과는 미리보기에서 확인하고 수정할 수 있다. CSV quoting 규칙을 적용하며 SMILES 문자열을 단순 문자열 분할로 읽지 않는다.

CID는 문자열로 보존한다. 같은 CID가 여러 번 나타나도 입력 행 ID로 구분해 결과가 덮어써지지 않게 한다. 원래 행 순서, 원본 SMILES, 처리한 SMILES와 오류를 보관한다. 잘못된 SMILES, 빈 값, 지원하지 않는 원자, 3D 생성 실패는 행별로 기록하고 다른 화합물은 계속 처리한다. 완전히 파싱할 수 없는 파일은 제출 전에 수정하도록 안내한다.

RDKit ETKDGv3로 conformer를 생성하고 MMFF를 우선 사용해 최소화한다. MMFF를 사용할 수 없으면 UFF 파라미터 지원을 확인한 뒤 대체하고 사용한 force field와 수렴 여부를 기록한다. 생성한 conformer 수가 요청보다 적거나 최소화가 실패하면 이를 결과 상태에 반영한다. RDKit은 conformer별 최소화 수렴 상태와 에너지를 반환한다. [RDKit conformer 문서](https://www.rdkit.org/docs/GettingStartedInPython.html#working-with-3d-molecules)

화합물의 원래 입체화학과 형식전하를 보존하는 것을 초기 기본값으로 제안한다. 수소 추가를 pH별 protonation 및 tautomer 탐색과 동일하게 취급하지 않는다. 여러 fragment를 포함한 SMILES는 가장 큰 유기 fragment를 사용하는 salt 제거 옵션을 기본 제안하고, 제거 성분과 변환 후 SMILES를 처리 결과에 남긴다. 주성분을 명확히 정할 수 없는 혼합물은 입력 오류로 안내한다. 자동 protonation 및 tautomer 열거는 별도 옵션으로 필요성을 검토한다.

## QuickVina 실행과 점수

결합 위치를 지정하는 이번 용도에는 QuickVina 2.1을 사용한다. 공식 프로젝트도 결합 위치를 알고 있을 때 QuickVina 2를 권장한다. 바이너리 또는 빌드 소스와 체크섬을 고정하고 ligand 및 receptor 준비 도구와의 호환성을 실제 실행으로 검증한다. [QuickVina 공식 저장소](https://github.com/QVina/qvina)

기본 옵션 후보는 `exhaustiveness=8`, 화합물당 conformer 1개, 결과 pose 1개다. `--num_modes=1`로 conformer별 최상 pose를 얻고, 여러 conformer를 사용하면 affinity가 가장 낮은 pose 1개를 최종 선택한다. Exhaustiveness와 conformer 수는 관리자 상한 안에서 학생이 조정한다. Seed, 실제 CPU 배정, 엔진 및 전처리 버전, 모든 파라미터를 작업에 기록한다. [QuickVina 옵션 구현](https://github.com/QVina/qvina/blob/master/src/main/main.cpp)

RDKit 최소화 에너지와 docking affinity는 별도 필드로 저장한다. Viewer와 점수표에는 affinity 단위를 kcal/mol로 표시하고, 실험으로 측정한 친화도가 아닌 docking score임을 설명한다. 모든 conformer가 실패한 화합물에는 점수를 임의로 채우지 않는다. 일부만 성공하면 최상 결과와 부분 실패 상태를 함께 제공한다.

## CPU 배분과 작업 큐

관리자가 설정하는 값은 전체 계산 CPU 한도, 동시 실행 학생 수, 기본 학생당 CPU, 학생별 CPU 재정의다. 예를 들어 학생 2명이 각각 CPU 4개를 배정받으면 총 8개를 점유한다. 배정된 CPU 합계는 전체 한도를 넘지 않아야 하며, 실행 중인 학생 수에도 별도 상한을 적용한다.

전처리와 screening은 공통 자원 관리 아래 별도 작업으로 실행한다. 같은 학생의 계산 작업은 한 번에 하나만 실행한다. 제출 순서를 기본으로 하되, 앞 작업의 사용자가 이미 실행 중이면 다른 사용자의 실행 가능한 작업을 선택한다. 작업 시작 시 자원을 예약하고 종료 또는 취소 후 반환한다.

Screening 하나를 배정받은 worker는 화합물, conformer 순서로 처리한다. Qvina의 `--cpu`와 RDKit, OpenMM, BLAS 계열의 thread 수를 함께 제한한다. Worker 프로세스와 하위 프로세스에 OS 수준 CPU 제한을 적용해 라이브러리의 자동 CPU 감지로 한도를 초과하지 않게 한다. 제한된 계산 worker와 웹/API 프로세스를 분리한다.

관리자 설정 변경은 신규 작업 배정부터 적용한다. 실행 중인 작업의 예약량보다 한도를 낮추면 실제 배정과 적용 대기 값을 구분해 보여주고 신규 배정을 멈춘다. 이미 실행 중인 작업은 기존 예약량으로 마무리하며, 즉시 회수가 필요하면 관리자가 해당 작업을 중단할 수 있다.

각 화합물 완료 시 결과와 진행 상태를 저장한다. 서버 또는 worker 재시작 후 완료된 화합물은 재실행하지 않고 미완료 항목부터 재개한다. 실행 중이던 화합물은 재시도할 수 있지만, 동일한 결과를 중복 반영하지 않는다. Worker heartbeat와 자원 예약을 대조하고 이전 계산 프로세스가 종료되었는지 확인한 뒤 예약을 회수한다. Redis 연결 장애 시 별도 로컬 executor를 임의로 켜지 않는다.

작업에는 대기, 준비 중, 실행 중, 부분 성공, 완료, 실패, 취소 상태를 제공한다. 화합물 timeout, 최대 재시도 수, 작업 취소, 실패 항목만 재시도를 지원한다. 취소와 timeout은 계산 하위 프로세스까지 종료하고 이미 완료된 결과는 보존한다.

## 결과와 저장 공간

결과 목록은 CID 검색, affinity 정렬, 처리 상태 필터, 페이지 단위 조회를 제공한다. Pose를 선택하면 receptor와 최상 ligand pose를 겹쳐 표시한다. 전체 완료 전에도 진행률, 성공 및 실패 개수, 완료된 점수를 조회할 수 있다.

다운로드는 전체 점수 CSV와 TSV, 성공한 화합물의 최상 pose SDF 및 PDBQT, 전처리 receptor, 실행 설정과 오류 보고서를 제공한다. 전체 점수표에는 실패한 입력 행도 포함하고 점수는 빈 값으로 둔다. 진행 중 다운로드에는 내보낸 시점과 미완료 상태를 기록한다. SDF 변환은 원래 분자의 결합 차수와 입체화학을 보존하는 경로를 검증한다.

100,000개 행과 대량 pose 파일을 한 번에 브라우저 메모리에 올리지 않는다. 다운로드와 묶음 파일 생성은 순차 처리하며, 계산 중간 파일은 화합물 처리 완료 후 필요한 결과만 남긴다. 데이터 보존 기간과 디스크 한도는 관리자가 지정하고, 삭제 전 대상과 사용량을 확인한다. 초기에는 결과 자동 삭제를 비활성화한다.

| NGL과 연동 sequence UI | 잔기 선택, grid box, 전처리 구조와 docking pose 표시 |
| FastAPI | 인증, 승인, 입력 검증, 작업 생성, 권한 검사, 결과 API |
| PostgreSQL | 사용자, 작업, 입력 행, conformer, 최상 pose, 자원 예약, 변경 이력 |
| Redis와 RQ | Worker 전달과 실행 알림. 작업과 복구 상태의 기준은 PostgreSQL에 둔다. |
| 계산 worker | PDBFixer, OpenMM, RDKit, PDBQT 준비 도구, QuickVina 실행 |
| Docker Compose와 reverse proxy | IP와 포트로 접속하는 단일 서버 배포, 데이터 영속화 |

원본 파일과 결과는 서버의 영속 저장소에 보관한다. DB에는 파일 위치와 체크섬, 조회에 필요한 메타데이터를 저장한다. 사용자 ID와 서버가 생성한 작업 ID로 저장 경로를 정하고 업로드 파일명을 실행 명령이나 경로로 직접 사용하지 않는다.

관리자 초기 비밀번호는 소스와 문서에 평문으로 넣지 않고 설치 시 비공개 설정으로 전달해 hash로 저장한다. 데이터 API와 파일 다운로드에 동일한 소유권 검사를 적용한다. DB와 Redis 포트는 학내망에 직접 공개하지 않고 웹 진입 포트만 제공한다. 초기 회원가입 항목은 ID, 이름, 학번, 비밀번호를 제안하며 이메일 인증은 필수로 하지 않는다.

## 운영 기본값 제안과 처리량 측정

현재 확인한 서버는 논리 CPU 64개, RAM 약 504GiB이며 Docker Engine과 Compose로 서비스를 실행한다. 설치 경로와 IP·port, 허용 네트워크는 비공개 배포 설정에서 관리한다.

초기 제안은 계산 CPU 상한 56개, 동시 학생 8명, 학생당 CPU 4개다. 기본 배정은 총 32개이고, 관리자가 측정 결과에 따라 동시 학생 수와 학생별 CPU를 조정한다. OS와 웹 서비스에 여유를 남긴다. Library 기본 상한은 100,000개이며 관리자가 낮출 수 있다. 학생별 대기 작업 수, conformer 상한, 저장 공간 한도도 설정 가능하게 한다.

작업당 상한을 모두 사용하면 40명 × 100,000개 = 4,000,000개다. 학생 8명이 동시에 실행하고 화합물당 5초가 걸린다고 가정하면 docking만 약 28.9일이다. 실제 측정값이 아니며 전처리, 여러 conformer, 실패 재시도 및 I/O는 추가된다. CPU를 늘릴 때 속도가 선형으로 빨라진다고 가정하지 않는다.

구현 초기에 대표 분자 50~100개로 CPU 1, 2, 4, 8개 배정의 처리량을 측정한다. 개별 docking 시간뿐 아니라 여러 학생 작업의 전체 처리량, 분자 유연성에 따른 시간 분포, 메모리와 결과 파일 크기를 기록한다. 이 결과로 최대 규모의 시간과 저장 공간을 추산하고 운영 기본값을 정한다.

## 구현 순서와 완료 기준

1. **실제 화학 계산 경로 검증**: PDB 전처리, RDKit 최소화, qvina 실행, 최상 pose 및 점수 추출을 작은 예제로 연결한다. Qvina와 PDBQT 준비 도구의 원자형 호환성, 원래 화학정보를 보존한 SDF 변환을 확인한다. 결손과 금속 사례의 지원 범위를 기록한다.
2. **회원과 관리자 기반**: DB migration, 가입과 승인, 로그인, 소유권 검사, 비공개 관리자 초기화, 자원 설정을 구현한다.
3. **입력과 viewer**: PDB 전처리 작업, sequence와 structure 선택 동기화, grid 설정, 구분자와 컬럼 선택, 입력 오류 미리보기를 구현한다.
4. **병렬 scheduler와 복구**: CPU 예약, 학생별 실행 제한, 순차 compound 처리, 상태 갱신, 취소, timeout, checkpoint, 재시작 복구를 구현한다.
5. **결과와 다운로드**: 최상 pose viewer, affinity 표, 전체 행 export, 진행 중 결과, 결과 묶음 다운로드와 저장 공간 관리를 구현한다.
6. **통합 검증과 배포 준비**: 실제 qvina 통합 실행과 자원 한도, 장애 복구, 대량 목록 및 export를 검증한다. 설치, 백업, 재시작, 운영 안내를 작성한다.

검증에서는 승인 전 실행 차단, 다른 학생 결과 접근 차단, 동시 실행 수 및 총 CPU 제한, 같은 학생의 화합물 순서, 중복 실행 방지, 중단 후 재개를 확인한다. Viewer는 같은 번호의 서로 다른 chain 잔기, insertion code, 복구된 잔기의 대응 관계를 확인한다. Library는 잘못된 SMILES와 중복 CID가 있어도 전체 입력 행과 결과가 대응하는지 확인한다.

실제 qvina 테스트와 대규모 상태 관리 테스트는 구분한다. 소규모 실제 계산으로 화학 경로를 검증하고, 대량 조회와 export는 20,000행 입력과 총 800,000행 결과로 검증했다. 작업당 100,000개로 확대한 후 최대 4,000,000개 전체를 실행한 부하 검증은 수행하지 않았다. 상태 관리용 가상 데이터 테스트를 실제 docking 처리량 측정으로 보고하지 않는다.

## 착수 범위

첫 구현은 위의 핵심 흐름과 운영 기능을 대상으로 한다. GPU docking, 외부 서열 기반 단백질 전체 모델링, MM/GBSA, MD, 자동 상호작용 해석, 외부 공개 서비스는 이번 범위에 포함하지 않는다. 포트와 내부 접속 주소는 설치 환경을 확인해 설정한다. 핵심 흐름과 운영 기능을 구현했으며 실제 검증 결과와 지원 범위는 [검증 기록](validation.md)에 정리한다.
